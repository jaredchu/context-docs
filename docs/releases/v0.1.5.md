# v0.1.5 — experimental prerelease

Bundles **context-docs 0.1.5** and **adopt-context-docs 0.1.6**.
Published on September 29, 2026 at `927d28c12c9a` as an
[experimental prerelease](https://github.com/jaredchu/context-docs/releases/tag/v0.1.5).
The [release commit CI run](https://github.com/jaredchu/context-docs/actions/runs/36507800666) passed.

A user-selected `Context Docs logging preference: auto` now enables JSONL during
adoption or authorized maintenance when Git confirms the project is outside a
repository and no explicit project logging setting exists. Existing `off`, `jsonl`
or other logging methods take precedence. Parent repositories, worktrees and bare
repositories count as Git; missing Git, broken repositories or detection errors
leave settings unchanged. Enablement is saved in project instructions, preserving
custom paths, original adoption dates and history. Adding Git later retains it.
Audits never enable logging. Installation alone does not select this preference.

Use the preference in a task request or already loaded personal/project instructions:

```text
Context Docs logging preference: auto
```

Update both complete skill folders together, preserving local customizations.
The [packaged guide](../../skills/context-docs/references/event-journal.md#optional-auto-preference)
defines precedence and the read-only policy helper. Ordinary Markdown maintenance
still needs no runtime; optional auto detection requires Python 3.9+ and Git.
The journal writer and schema are unchanged. No background capture or automatic
committing is introduced.

## Validation and limits

The [implementation CI run](https://github.com/jaredchu/context-docs/actions/runs/36505221964)
passed all 99 regression tests plus study controls and report regeneration.
Both skill metadata validators and repository static checks passed separately.
Eight new policy tests cover real Git topologies and conservative error handling.

The [native evaluation](../../evals/results/2026-09-29-auto-preference/README.md)
retains six sessions: two initial Codex harness blocks, then four functional passes
across Claude and corrected Codex conditions using identical candidate packages.
Only the confirmed no-Git project gained one setting line. Explicit off, default-off,
parent Git, worktree and broken-repository projects remained unchanged. Repeat
maintenance after Git initialization and a separate audit wrote nothing.

These are direct candidate-file evaluations, not proof of automatic skill selection
or global preference loading. Claude retained guard denials and enumerated journal
filenames during a broad search. Functional preservation is not a clean pass for
avoiding unnecessary history access or unrestricted-client behavior. No general
reliability, logging necessity or recording-cost advantage is established.

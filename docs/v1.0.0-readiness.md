# v1.0.0 graduation criteria and release readiness

Status: **proposed criteria; not ready for a stable release**. Evidence reviewed
October 11, 2026, against released v0.1.9. This document prepares a maintainer
decision; it does not approve these proposed gates, start evaluations, authorize
outreach or publication, or change the current experimental status.

## What graduation means

v1.0.0 would commit to a documented, supported workflow for preserving decisions,
their rationale, current work, blockers and next steps across AI sessions.
Users still review consequential edits and explicitly load context when resuming.
The skill guides an agent; stable status would not guarantee perfect recall,
factual correctness, privacy, automatic skill selection or concurrent-edit safety.

The proposed stable scope is core initialization, maintenance and read-only audit,
plus adoption and upgrades in supported Codex and Claude Code configurations.
Shared Markdown and opt-in local-only context are proposed for inclusion. Storage
remains an explicit choice; existing project setups and explicit logging settings win.
Optional event logging must receive a separate support decision: include it only
with evidence for its documented behavior, or retain a clearly labeled experimental
extension without making ordinary Markdown use depend on it. Follow the existing
[journal requirements](event-journal-pilot.md#requirements-before-broader-integration)
before broadening its integration.

The compatibility contract should identify supported client versions, operating
systems, installation scopes and instruction-loading routes. Treat skill names,
documented operations, adoption/discovery conventions, storage and logging settings,
packaged references and any supported journal schema as public interfaces. Preserve
equivalent existing layouts, adoption dates, entry points, customizations and history;
document any deliberate migration instead of silently applying it.

If adopting [Semantic Versioning](https://semver.org/), define those interfaces
before 1.0.0, use patch releases for compatible fixes, minor releases for compatible
features and major releases for incompatible changes. The bundle, sibling skills
and standard have separate version identities; record their exact versions and
hashes. Decide which components graduate and remove experimental wording only
for those components, including the canonical [standard](../skills/context-docs/references/standard.md)
if it graduates. Do not rewrite older experimental release records.

of statistical reliability. The maintainer must accept the scope and criteria
before new release-gating evaluations are frozen. Every gate needs a dated result
and evidence for the candidate being released; older results are supporting
evidence, not automatic passes for changed packages.

For G2, define evidence separately for catalog availability, actual skill use,
instruction consultation, automatic startup loading and context reading. A catalog
entry proves availability; trace-observed reads prove consultation, not automatic
startup loading. Agent self-reports alone do not prove either. Use client startup
or debug evidence when available. Where startup loading is unobservable, disclose
it as unknown and validate an explicit instruction/context-read route; the
maintainer must accept that route and limit the stable promise accordingly before
the freeze. Do not demand unavailable telemetry or silently count explicit loading
as automatic loading. Normal-work maintenance still needs an observed journey
under whichever supported instruction-loading route is chosen.

For G4, freeze whether Git index bytes must remain identical, or whether verified
index stat-cache refreshes are allowed while staged entries/content, objects, refs
and history remain unchanged. A permitted refresh needs evidence of its metadata-only
nature and client origin; unexplained drift cannot pass that exception. Likewise
identify allowed CLI-managed runtime/cache changes separately from protected
project/client settings before execution. Investigate unexplained configuration
additions or mutations without reverting unrelated work. Unexplained drift in a
candidate run remains an open gate gap, not proof that the skill caused the change.
Historical unknown causes may remain unknown: disclose them and decide candidate
readiness from fresh frozen baselines and runs, preserving the earlier failed
result rather than requiring an unrecoverable historical attribution.

For G5, freeze participant eligibility, project selection, scope, effort measures,
completion criteria and budgets before recruitment/execution. Use a small pilot
with varied layouts and both supported clients; state its actual coverage rather
than inventing a universal participant count or reliability threshold. Ordinary
daily use does not require an evaluation log. The
[outside-contributor packet](../evals/external-validation/README.md) governs external
case/review independence. For this gate, the excluded author/collaborator group
includes the maintainer and every model/client involved in design, implementation,
execution or review, including GPT 6.1 Sol, Claude Opus 5.5 and Codex/Claude Code
sessions; a fresh collaborating-model session is not outside review.
The [quality protocol](../evals/quality-protocol.md)
provides retention, authority and reader checks. Keep a reserved case out of tuning
when available and disclose when there is no holdout. Pilot completion alone is
not a pass: assess outcomes against the frozen criteria and blocker list, retaining
any assistance or correction needed. Material failures block graduation unless
the supported scope is explicitly narrowed and the affected checks rerun.

The release does not need to outperform expert maintenance. An absolute usability
pilot can establish whether the documented workflow works for its participants.
Claims of reduced effort or improved accuracy require matched comparisons and
actual measurements; fewer reads, tokens or file bytes do not establish those
claims. Remove or qualify unsupported claims rather than treating a stable label
as proof of benefit.

## Release blockers and failure handling

A material failure in the proposed stable scope blocks graduation until fixed and
verified, or until the maintainer explicitly narrows the supported scope and
updates the guide and release criteria. Do not waive a failure by averaging scores.
Blockers include:

- Losing a unique decision, its rationale, an active constraint, blocker or next
  step needed for the handoff.
- Inventing approval, completion or deployed/runtime state, or presenting a known
  stale claim as current without checking relevant evidence.
- Overwriting unrelated work, local customizations, existing settings or saved
  records; writing during a read-only audit; changing staged content or history
  without authorization.
- Unauthorized additions, removals or changes to project/client configuration by
  the workflow. Unexplained configuration drift leaves G4 open until investigation
  distinguishes workflow effects from unrelated activity.
- Copying local-only content into shared documents without authorization, or
  writing local-only context/journals without required tracking and ignore checks.
- A documented supported installation, discovery, adoption, upgrade or continuation
  route that cannot complete, with no supported documented recovery.

Distinguish a client runtime/cache or index-metadata change from a substantive
content/settings mutation, but investigate and disclose either when observed.
The installed smoke check's strict index-byte failure remains a failure under its
original criteria; this plan does not retroactively rescore it. Resolve its impact
on G4 before sign-off. Preserve original attempts, freezes, artifacts and scores.
Give focused fixes new regression cases and fresh identified candidate runs;
do not overwrite failed trials or silently change criteria after seeing results.

### Remaining before a release decision

- [ ] **G1:** Maintainer accepts the proposed graduation criteria, support matrix,
  compatibility rules and component support boundaries, including logging.
- [ ] Freeze a candidate package/hash manifest, test matrix, source-backed
  criteria, allowed writes, preservation baselines and bounded execution plan.
  Record client versions, requested/observed model identities, installation and
  setting scopes, and native loading evidence available for each route.
- [ ] **G2–G4:** Complete supported native journeys and candidate regressions;
  verify fresh readers actually consult context. Cover stale/conflicting sources,
  existing layouts, local-only storage, audit, repeat setup and customized upgrades.
- [ ] **G4:** Record the disposition of historical Git metadata drift, unexplained
  Codex configuration additions and Claude global runtime-state changes, retaining
  unknown causes. Verify the final candidate against fresh frozen preservation
  baselines and acceptable Git metadata/runtime exceptions; distinguish protected
  project/client configuration from CLI-managed cache/state.
  Support claims must match what was actually verified.
- [ ] **G5:** Align the contribution packet's collaborator listing with the G5
  exclusion before soliciting cases/reviews. Pass the frozen outside-user pilot
  and resolve material findings from outside artifact review;
  retain outcomes, corrections, failures, exposure and independence declarations.
- [ ] **G6:** Complete checks for whichever logging behavior is in stable scope,
  or clearly label and isolate the experimental extension in packages and guide.
- [ ] Resolve every material supported-scope blocker and obtain focused
  counterpart review under the [collaboration policy](../AGENTS.md#model-collaboration).
  Collaborating-model review does not substitute for G5 outside review.
- [ ] **G7:** Prepare the candidate's versions, changelog, release notes, support
  matrix and upgrade guidance. Align README, guide, packaged status wording and
  website with the agreed scope while preserving historical evidence.
- [ ] Run `python3 evals/checks/static_checks.py`, applicable regression suites,
  `python3 -m unittest discover -s site -p 'test_*.py'` and `python3 site/build.py`
  on the final candidate; require its applicable GitHub Actions workflows to pass.
  Preserve studies and existing setups; build/regenerate reports in disposable
  outputs where needed. Mechanical passes remain separate from behavioral gates.
- [ ] Record a maintainer **go/no-go** decision against G1–G7, with evidence links,
  scoped limitations, any excluded features and publication authorization.

### Publication and post-release verification

- [ ] After authorization, publish a new v1.0.0 tag/release at the verified commit
  without the GitHub prerelease flag; verify package contents and identities.
  Existing release contents and history remain unchanged. Credit actual Codex and
  Claude assistance under the [attribution policy](../CONTRIBUTING.md#commit-attribution).
- [ ] Deploy the approved website build and verify live pages, downloadable
  content and status against that same release. Record commit, Actions and hashes.
- [ ] Publish supported configurations, remaining limitations, issue-reporting
  and upgrade guidance. Decide whether to support a rollback procedure and verify
  it before documenting that additional commitment. Installed upgrades are a separate
  authorized action; never silently re-adopt projects or alter local preferences.

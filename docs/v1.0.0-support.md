# Proposed v1.0.0 support matrix and compatibility rules

Status: **for maintainer review; not an approved support policy**. Prepared
October 11, 2026, from the v0.1.9 guide and evidence. No v1.0.0 package, minimum
client version or supported environment has been certified. The published release
remains experimental. This proposal supplies G1 of the
[graduation criteria](v1.0.0-readiness.md#proposed-graduation-gates); accepting it
would not complete G2–G7 or authorize publication.

## Recommended initial scope

Start with local macOS projects in Codex CLI, Codex desktop and Claude Code CLI.
Validate both user-scope and project-scope sibling skill installations, shared
Markdown and explicitly selected Git-ignored context. Core may be used alone;
adoption requires the sibling core. Keep event capture and auto-enable resolution
as an experimental extension for the initial stable release, while protecting
existing logging settings and records in every upgrade.

This is a scope recommendation, not a restriction on current users. Linux,
Windows, other agents and additional execution environments remain unvalidated
for a stable promise until the maintainer expands the matrix and obtains evidence.
Ubuntu CI verifies repository mechanics; it does not establish a Linux native
agent journey. Existing installations and project conventions remain in place.

Stable support would mean reproducing and addressing defects in the agreed
configuration matrix while preserving the compatibility contract below. It would
not mean guaranteed agent accuracy, a response-time commitment, arbitrary model
support or automatic updates on every prompt. Ordinary work should maintain
context through the project's loaded rule; explicit maintenance remains a
documented recovery when an update is missed.

combinations rather than claiming an untested version range. Minimum versions,

instead of switching routing merely because a client gains a new capability.
Managed-only sessions or settings that suppress the selected skills/instructions
are outside the proposed ordinary-maintenance promise unless an explicit supported

## Project and feature matrix

These rows describe proposed feature boundaries, not a full cross-product promise.
Support covers only client/scope/platform/project-mode combinations explicitly
enumerated and passed in the frozen validation matrix. Publish that list as the
support statement. Unlisted combinations remain unvalidated even when their
components pass elsewhere; selecting the list is a maintainer scope decision.

| Mode or feature | Proposed v1.0.0 disposition | Compatibility boundary and evidence gap |
| --- | --- | --- |
| Core initialize, maintain and audit | Stable target | Initialize/maintain use source-backed facts and retain decisions/rationale/open work. Audit changes no documents, instructions, ignore rules or journal. Repeat/no-change maintenance avoids bookkeeping edits. Candidate journey and semantic checks remain pending. |
| Adoption and repeat adoption | Stable target | Merge or reuse effective guidance and a meaningful marker; preserve equivalent layouts, dates and authority. Do not duplicate rules, silently re-adopt or claim automatic loading from a filename alone. Candidate instruction-route checks remain pending. |

## Public compatibility contract

The proposed contract concerns supported workflow behavior and persistent project
interfaces, not exact prose, example filenames, template headings, model choices
or internal implementation details.

| Interface | Proposed guarantee within a stable major version |
| --- | --- |
| Package identity | Preserve `context-docs` and `adopt-context-docs` names and complete portable packages. Core remains usable alone; adoption resolves its sibling core without inventing a substitute. Publish exact compatible package tuples; equal version numbers are not inherently required. |
| Operations and knowledge semantics | Preserve initialize/maintain/audit intent, read-only audit, meaningful-change maintenance, source/authority distinctions and decisions/rationale/unfinished work. Changes in formatting are compatible only when they preserve meaning and usability. |
| Project guidance and discovery | Recognize existing equivalent maintenance rules, adoption markers and entry points. Keep `Method: context-docs`, `Adopted:` and `Entry point:` meanings, including a valid relative path or shared README section; preserve the original date or recorded `unknown`. |
| Storage | Preserve the explicit shared/local-only choice and equivalent `Context storage: local-only` guidance. No upgrade silently selects local-only, untracks context, changes global Git excludes or makes ignored content shared. |
| Logging settings and existing history | Preserve explicit `Event journal:` settings, directories and records. Explicit settings, including `off`, always beat auto; preserve any recorded opt-in auto preference. Installation, upgrade and audit never enable logging or apply auto. These preservation/default/precedence rules are stable targets; auto's eligibility conditions and execution remain experimental. |
| References and document roles | Keep documented roles and authority semantics compatible, with portable packaged references and supported entry links. Changing a published path requires preserving its compatibility route or releasing a deliberate breaking change. Existing project layouts do not need to match templates. |
| Authorization and boundaries | Maintenance adds no authority to commit, publish, deploy, schedule, modify global settings or move private content into shared destinations. Respect the user's authorized scope and protect unrelated work. |

Under the proposed initial scope, journal CLI flags/output, on-disk JSONL schema
and auto's eligibility conditions (including no-Git and ignored/untracked local-only
checks) are **not stable interfaces**. Experimental
changes still preserve existing records/settings, disclose incompatibilities and
require authorization for migrations; experimental does not mean disposable.
If the maintainer elects to graduate logging, add those interfaces, supported
runtime versions and recovery/failure checks to the contract before the freeze.
The current helper requires Python 3.9+, as documented; that is not a promise for
every Python release or operating system.

## Versioning and upgrade rules

Use [Semantic Versioning](https://semver.org/) for components that graduate:

- **Patch:** compatible corrections to instructions, packaging or implementation.
  A wording change that changes an interface's meaning is not automatically a patch.
- **Minor:** compatible additions, including explicitly validated support rows or
  optional features that do not change existing defaults or require migration.
  Deprecate a stable interface with notice and a working compatibility route.
  The explicitly excluded experimental interfaces have the separate minor-release
  exception described below.
- **Major:** removing/renaming a stable interface, changing defaults or precedence
  incompatibly, raising a supported minimum incompatibly, or requiring project
  migration. Deliberately removing a declared supported package tuple or environment
  combination also breaks the support contract and requires a major release;
  adding one is a compatible minor change.
  Provide rationale, migration guidance and a separately authorized path.

The proposed v1.0.0 bundle graduates core/adoption workflow behavior and the
standard's roles/authority semantics. Their exact versions and package hashes
must be declared in the candidate manifest; sibling skills, standard and bundle
advance independently. No `VERSION` file or standard status changes in this task.
Because the experimental helpers ship inside core, incompatible changes confined
to those explicitly excluded interfaces may ship in a **core minor release**, with
prominent changelog/upgrade disclosure. Compatible experimental fixes may be patches.
Neither may break stable defaults/precedence or the preservation contract. Keep
existing records unchanged and readable through an available prior or compatible
reader; any optional migration is separately authorized and preserves originals.
Graduating those interfaces requires an explicit support decision and compatible
public contract. Never replace a published
version's contents or rewrite saved evaluations to match new criteria.

The first stable upgrade target should be released core/adoption **0.1.9/0.1.9**
and standard **0.1.1**, both unmodified and locally customized, in every supported
installation scope. Older installations are preserved in place; supporting their
direct upgrade requires separate declared tuples and checks. A version mismatch
or unknown source is reported before copying, not treated as permission to replace.

An authorized upgrade should inventory existing packages and customizations,
retain a recoverable copy, review differences and install complete compatible
siblings. Project-scope packages may be tracked/shared repository files: their
upgrade is a reviewable project change, with no implied commit or publication.
Preserve project rules, marker dates, entry paths, storage/ignore choices,
logging preferences, settings and saved history. Do not rerun adoption, migrate
documents, capture setup events or change global instructions as a side effect.
If a required change conflicts with local edits, resolve that change explicitly;
preservation does not require silently accepting incompatible behavior.

Do not promise a rollback procedure until restoration of both package files and
customizations is tested. Package restoration does not undo project edits or
recover missing local-only documents. The user's existing backups/transfer method
remains responsible for those files; no new backup service is provisioned.

## Acceptance evidence and review decisions

G1 approval selects the rows and contract; G2–G7 still require candidate evidence.
For each accepted route/mode combination, freeze source snapshots, allowed writes,
settings/Git baselines, loading evidence, model/client identity and pass criteria.
Use an explicit instruction/context-read fallback only with a scoped promise;
trace reads prove consultation, not automatic startup loading. Ordinary work must
be exercised without naming the skill on every prompt, under the chosen loaded
rule. Retain failures and distinguish that test from unconstrained implicit selection.

Preservation checks cover ignored/untracked files, local customizations, instructions,
settings, saved study artifacts and Git staged content/history. Freeze any permitted
client stat-cache/runtime changes separately; investigate unexplained configuration
drift without reverting unrelated work. Historical smoke failures remain unchanged.
Apply the [G4 drift rule](v1.0.0-readiness.md#proposed-graduation-gates) to new
candidate runs, not retroactive rescoring. Mechanical CI cannot substitute for
native journeys, semantic checks or outside-user review.

The maintainer review should decide:

- [ ] Accept or adjust initial local macOS support, including Codex desktop and
  both installation scopes; identify any additional platform/environment rows.
- [ ] Choose exact candidate client/OS/model combinations and what evidence counts
  for instruction routing; no minimum/range is implied by the observed versions.
  Decide notice and handling for upstream client/model retirement or breakage;
  this proposal does not guarantee third-party availability.
- [ ] Accept shared/no-Git/local-only storage and worktrees as stable targets, with
  the required combinations recorded in the validation matrix.
- [ ] Keep logging experimental as recommended, or expand the stable contract and
  validation scope before accepting it.
- [ ] Accept the public interfaces, SemVer rules, v0.1.9 upgrade target and
  customization/conflict handling; decide older-version support, including the
  v0.1.8 bundle's core/adoption 0.1.8/0.1.9 tuple, and any rollback support.
- [ ] Record the decision and rationale, then freeze a bounded validation plan.
  Approval of this proposal alone grants no study execution, outreach or publication.

No checklist item is accepted or empirically passed by writing this document.

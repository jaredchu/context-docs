# Bounded v1.0.0 validation plan

Status: **proposed for review; not frozen or authorized for execution**. Prepared
October 11, 2026. This plan operationalizes native journeys, upgrades and
preservation for G2–G4 of the [graduation criteria](v1.0.0-readiness.md).
The [support matrix](v1.0.0-support.md) and exact candidate/configurations still
need maintainer acceptance. No new subject sessions, installation changes or
v1.0.0 validation results are created by this document.

The separate [Wave 1 preparation](../evals/v1-readiness/wave1/README.md) provides
synthetic recipes, proposed exact prompts, a mechanical checker and read-only
isolation evidence. It establishes no executable authenticated profile or native
outcome. Current packages match v0.1.9; a distinct accepted candidate and the
remaining isolation/review prerequisites are required before an execution freeze.

## Scope and sequence

Use two waves. Wave 1 probes the two mainstream user-scope CLI routes and negative
boundaries before spending allowance on more routes. Stop for a recorded review
of its results. Wave 2 requires a separate scope/budget and execution decision;
it is not an automatic continuation. Passing Wave 1 alone does not establish the
full proposed support matrix or permit graduation.

Test a pinned candidate in new synthetic, disposable projects. Do not use this
repository's real context, installed skills, journals or saved studies as writable
subjects. Only the accepted combinations listed below are candidates for support;
passing components does not certify an untested cross-product. G5 outside-user
validation and G7 release/deployment remain separate work. Logging capture/auto
eligibility stays experimental under the recommended G6 disposition; test its
stable preservation/default/precedence boundaries without broadening integration.

## Proposed combinations

All combinations use local macOS; exact OS release, architecture, client build,
model request, identity-evidence requirement and instruction route are filled at
the freeze. Record responding identity after execution, or its specific verification
limit. `C1`–`C5` refer to the [support routes](v1.0.0-support.md#client-and-installation-matrix).
Each combination gets its own files, client session state and package selection.

| ID | Wave | Client/scope | Project and storage | Required configuration |
| --- | --- | --- | --- | --- |
| V1 | 1 | C1: Codex CLI, user scope | Standard Git repository, shared context | Native user-scope discovery; effective project guidance |
| V6 | 1 | C4: Claude Code CLI, user scope | Standard Git repository, shared context | User skills exposed; loaded Claude guidance/import |
| V2 | 2 | C1: Codex CLI, user scope | Standard Git repository, local-only context | Explicit storage choice, verified ignored/untracked paths and agreed local discovery route |
| V3 | 2 | C2: Codex CLI, project scope | Git worktree, shared context | Project packages selected; real worktree exclude/index locations |
| V4 | 2 | C3: Codex desktop, user scope | Standard Git repository, shared context | Recorded desktop build, new app sessions; actual app evidence |
| V5 | 2 | C3: Codex desktop, project scope | No-Git project, shared local Markdown | Project package discovery; Git absence established rather than assumed |
| V7 | 2 | C4: Claude Code CLI, user scope | Standard Git repository, local-only context | Same storage checks as V2; effective instruction route verified |
| V8 | 2 | C5: Claude Code CLI, project scope | Git worktree, shared context | Project packages selected; effective instruction route verified |

V3/V8 do not certify project-scope ordinary repositories; V5 does not certify every
no-Git client. Those additional combinations require an amended support decision,
freeze and budget. Direct Claude `AGENTS.md` loading is not an extra uncounted
sub-route: select one evidenced instruction route per combination. Additional
routes require additional identified cases. Desktop results cannot be replaced
by CLI results. If a combination is removed, narrow the proposed support statement
explicitly rather than declaring it passed.

## Isolation and preflight

The [concrete isolation setup proposal](v1.0.0-wave1-isolation-setup.md) recommends
a dedicated macOS guest after read-only inspection found no qualifying existing
environment. Its provisioning route requires an explicit amendment to the
existing-environment-only condition below and separate setup/login authorization;
the proposal has not changed that condition or authorized execution.

Before freezing inputs, select an existing supported disposable client profile or
test OS account with subscription-authenticated access and genuinely isolated
skill/configuration locations. This plan provisions no account or service and
does not authorize spending. Do not overwrite the owner's actual skill folders,
global instructions, configuration, project rules or local excludes to obtain a
test. Do not substitute a supplied skill-file path in the prompt for native
discovery, or suppress user settings and then claim a user-scope pass.

If supported isolation cannot provide real user/project scope and preserve the
owner's setup, record that route blocked and stop before launch. Do not fall back
to the real installation. CLI-specific isolation and settings differences must be
documented; the result supports that configuration only. Desktop test profiles
must be verified separately. Run no subject with inherited hooks/MCP integrations
that can touch unrelated work; use a clean supported profile and report its settings
rather than silently altering the owner's environment.

The concrete isolation mechanism is unresolved. Naming a profile does not prove
isolation or claim every client offers one. Establish its supported behavior and
owner-file boundaries before preparing an executable freeze.

Map credential stores, app containers and cross-session memory/history as well as
skill/config files. A separate profile is insufficient if it shares protected
state with the owner's installation. Use an existing separate test OS account
where supported isolation cannot cover those stores; otherwise block the route
before freeze. Record store boundaries and non-secret preservation evidence;
do not copy credentials into fixtures or receipts. No login or profile operation
may alter an unprotected owner store.

Use GPT 6.1 Sol for Codex and Claude Opus 5.5 for Claude, through existing
subscription access. Record requested and observed identities separately; do not
claim an unexposed responder identity. No Astra, API/provider fallback, extra paid
access, model substitution or delegation inside subject sessions. An unavailable
client/model, required identity evidence or usage allowance is a stop condition.

Preflight checks, performed on copies after execution authorization, should:

1. Validate candidate metadata, packaged links/versions and standalone sibling
   resolution with repository static checks and applicable existing regression suites.
2. Verify the temporary profile, selected package hashes, scope visibility,
   instruction route and preservation inventory without sending a model request.
   Evidence requiring an agent request belongs in its counted subject session.
3. Build new fixtures and an evaluator-only atomic evidence ledger. Include a
   source/configuration conflict, approved decision/rationale, unapproved proposal,
   unresolved blocker/next step, unknown runtime state and unrelated unfinished work.
4. Validate the checker against a supported reference and corrupted controls:
   lost decision, invented approval/runtime state, stale current fact, write outside
   scope, audit write, ignore negation, tracked-local target and shared leakage.
5. Freeze the manifest before any subject execution. Keep answer keys, this plan,
   reviewers' notes and controls inaccessible to subjects. Do not expose protected
   owner files to subjects merely because their hashes are being monitored.

## Native journey: five fresh sessions per combination

Install complete candidate packages in the disposable profile/project as a
coordinator step using the documented route, preserving the installation receipt.
Installation is not proof of loading. Each phase below starts a fresh native chat
without earlier chat history; its allowed evidence is the current frozen fixture.
Only approved project artifacts carry forward. Freeze the next phase's inputs
and allowed writes after the preceding receipt, including coordinator-supplied
new evidence. Never copy expected answers into a task prompt.

Before J1, freeze the disposable profile's memory/history behavior and store
boundaries. Each fresh session must exclude resume, automatic memory and retrieval
of prior-session content; use supported controls in the test profile only. Retained
transcripts/receipts may exist as inaccessible archives, not subject inputs. Before
J3 and U2, verify no prior-phase facts can be injected from those stores. If that
cannot be established, or prior content is loaded from them, mark the phase
incomplete. Context-read evidence alone does not resolve that contamination.

| Phase | Cap | Task and allowed changes | Pass evidence |
| --- | --- | --- | --- |
| J1: adoption/initialization | 180 seconds | Explicit native adoption invocation. Create/maintain context and merge only agreed project guidance/marker/discovery/ignore changes. | Actual selected adoption/core package; context derives current facts from sources, retains decision/rationale/open work and reports loading separately. Local-only tracking/ignore checks precede writes. |
| J2: ordinary work | 180 seconds | A small synthetic code/config task with new approved work evidence; task does not name the skill or request a documentation update. Only named code/config and affected canonical context may change. | Loaded maintenance rule is consulted; context reflects meaningful work and current sources without losing decisions or promoting proposals. A manual reminder is recorded as a missed-update failure, not an automatic-maintenance pass. |
| J3: fresh-session continuation | 180 seconds | Neutral request to read the context entry point and continue its next task; no earlier conversation or supplied answers. Permit only the named continuation task and its affected context. | Trace/app evidence shows context consultation before the consequential continuation; answers/actions preserve rationale, authority and blockers. Record unsupported claims and justified unknowns. |
| J4: audit | 120 seconds | Explicit core audit only; report gaps, no project/package/settings/index/journal edits. | Read-only output and exact protected-byte/file-set preservation; findings have sources. A tool/read self-report alone is insufficient. |
| J5: repeat/no-change | 120 seconds | Repeat adoption, then maintenance with no new durable evidence. Permit no edits/events when equivalent setup is already complete. | Original marker/date/paths/guidance/logging/history retained; no duplicated rule or bookkeeping. Missing new evidence is not a reason to rewrite. |

Each phase is one attempt, not a prompt-repair loop. A missing dependency,
unconfirmed loading or permission failure must be recorded with its actual result.
An honest unresolved result is useful evidence but does not pass a required positive
journey. A hard content/scope failure stops downstream phases for that combination;
mark them not run. Do not propagate corrupted artifacts as a passing baseline.

## Upgrade checks: two variants, two sessions each

For every selected combination, prepare two **new** pre-adopted v0.1.9 fixtures,
separate from J1–J5. Both contain core/adoption 0.1.9, standard 0.1.1, dated project
guidance, existing context and synthetic saved study/journal sentinels. One has
unmodified installed packages; the other has benign uniquely identified package
customizations and equivalent project instructions, paths and storage choices.
Freeze every customization and required preservation item before execution.

Give each upgrade variant its own isolated package/profile state, separate from
J1–J5 and the other variant. Before U1, verify installed package hashes against
v0.1.9 and candidate absence across effective scopes, including fallback locations.
The fixture manifest must establish the old selection; any native selection
confirmation is part of U1's counted session, not an extra preflight model call.
Do not run U1 against a location where the journey already installed the candidate.

| Phase | Cap | Scope and acceptance |
| --- | --- | --- |
| U1: authorized test upgrade | 240 seconds | Upgrade only the disposable packages from the pinned release to the candidate. Inventory differences/customizations, retain a recoverable copy and install complete compatible siblings. Preserve local edits or report a real conflict without overwriting. Project files, markers/dates, entry/storage/ignore/logging choices, journals, sentinels and Git staged content/history stay unchanged. No adoption, setup event, commit or publication. |
| U2: fresh post-upgrade use | 180 seconds | In a new session, verify actual candidate selection and consult existing context for one small meaningful update under its existing maintenance rule. Preserve the old decision/rationale/open work and package customizations. Only the named synthetic update and affected context may change; do not silently re-adopt or migrate. |

Use the unmodified variant with explicit logging `off` and a preselected `auto`
preference; off must win. The customized variant has explicit `jsonl`, its original
directory and existing synthetic records. U1 must preserve them without capture.
For U2, allow only a separately inventoried append in an enabled journal when a
meaningful event warrants it, preserving the original byte prefix and records.
This checks preservation of an existing enabled setup, not graduation of capture.
For local-only variants, the journal destination must already be ignored/untracked.
If capture is blocked, record the gap and assess the stable preservation contract
separately from the experimental capture result.

A benign customization deliberately chosen to be compatible must survive a
completed upgrade. Reporting an invented conflict is not a pass. If a real
candidate conflict exists, score honest preservation/refusal separately from
upgrade completion; U1 remains incomplete and U2 is not launched. Conflict repair
needs a separate identified fixture/freeze. Older upgrade tuples and rollback are
outside this wave unless the maintainer revises scope and budget before launch.

## Wave 1 boundary batches

Use two additional CLI sessions per client: one 180-second core-only session for
B1, then one 240-second paired-package batch for B2–B4. These are four sessions
with eight case observations, not eight independent trials. Isolate the core-only
and paired profiles; freeze each case's writes/outcome beforehand:

- **B1: core alone/no Git.** Install only core for this case; initialize source-backed
  Markdown through native core invocation, then request the unavailable adoption
  skill with no fallback authorized. Require an honest missing-skill report and no
  further project/package/global changes. This is a boundary
  probe, not a complete supported no-Git journey.
- **B2: already tracked local context.** Request local-only setup without migration
  authorization. Require tracked-file detection, preserved content/history and an
  unresolved migration report; no silent untracking/deletion or privacy claim.
- **B3: ignored-entry discovery and sharing.** Name an ignored local entry point
  containing synthetic canaries, decisions and pending work. Request one separately
  supplied public API fact in shared docs. Require direct local discovery, unchanged
  local originals and no copied/paraphrased private content in shared outputs.
- **B4: explicit off and exposed journal.** An opted-in auto preference coexists
  with explicit off and a journal destination exposed by an ignore negation.
  Require settings/history preservation, no auto enablement, no event and no
  silent ignore repair. Explicit off wins without auto eligibility probing.

Freeze B1 as a core-only package environment distinct from paired-package cases;
do not leave the sibling installed or mask its absence with another scope.
The adoption-wrapper/missing-core dependency is a separate mechanical preflight
control, not a claimed native observation from B1.
Positive ignored/untracked storage belongs in V2/V7; B4 does not prove auto
eligibility or ignored-journal validation. Canary absence is a mechanical check;
semantic inspection must also detect paraphrase leakage. Keep all boundary results
separate from native-journey passes and general privacy claims.

## Counts and hard bounds

| Work | Wave 1 | Wave 2 | Maximum subject time |
| --- | --- | --- | --- |
| Journeys: five sessions per combination | 2 × 5 = 10 | 6 × 5 = 30 | 8 × 780 seconds = 104 minutes |
| Upgrades: two variants × U1/U2 per combination | 2 × 4 = 8 | 6 × 4 = 24 | 16 × 420 seconds = 112 minutes |
| Boundary core-only sessions and paired batches | 4 | 0 | 2 × 180 + 2 × 240 seconds = 14 minutes |
| Total subject sessions | **22** | **54** | **76 sessions; 230 minutes of capped subject time** |

Wave 1's subject cap is **68 minutes**; Wave 2's is **162 minutes**. These are
maximum session durations, not cost/latency predictions, total project effort or
independent sample counts. A time cap includes startup and human/tool interaction
inside that subject session, including manually timed desktop sessions. Stop a
phase at its cap; record unfinished work as timeout/incomplete rather than pass.

Per wave, cap coordinator fixture/checker/freeze preparation at 120 minutes and
post-run verification/reporting at 90 minutes. Reserve one counterpart protocol
review and one focused follow-up, each at most 90 seconds, before its freeze.
If more work is needed, preserve progress and request a revised budget instead of
starting subjects with an incomplete checker. Both waves' maximum elapsed-work
budget is therefore **656 minutes**: 230 subject + 420 coordinator + 6 reviewer.
Approval waits between waves are not active work or permission to continue.
Run one subject at a time; no background or overnight continuation is authorized.
Stop earlier on allowance limits; do not buy access or switch providers.

Freeze an exact user-prompt sequence per phase for both CLI and desktop, alongside
any available agent-turn cap. Use at most 20 agent turns per CLI session. J5 may
have two predeclared prompts (repeat adoption, then no-change maintenance); J1's
fixture must supply setup choices/authorization in advance. No corrective,
hinting or unscheduled agreement prompts are allowed. Extra user prompts are a
protocol deviation and leave the phase incomplete. Prompt sequences remain within
the existing session counts and wall-time caps.
If a client cannot enforce the turn cap, record that limitation and enforce its
wall-time bound. Available usage/token receipts are diagnostics, not cost savings.

No replacement attempts or uncounted diagnostic sessions. A failed timeout/parser/
startup attempt consumes its slot. An infrastructure error is not a semantic
failure, but leaves the required evidence incomplete. Check already captured
artifacts without another inference call when possible. Material fixes require
new case IDs, a new freeze and separate budget/authorization; retain the original
attempt and scores. No additional review rounds beyond the stated two per wave.

## Preservation and scoring

Before and after each phase, inventory the entire disposable fixture and selected
test-profile skill/configuration files: paths, bytes/hashes, modes, symlink targets,
ignored/untracked descendants and permitted generated files. Include the mapped
credential/app/memory/history store boundaries and supported preservation evidence;
blocked or inaccessible shared stores cannot be treated as unchanged. Also monitor owner
setup files and saved study artifacts read-only from the coordinator. Do not open
historical journals for routine context; hashing to prove preservation is distinct
from asking a subject to investigate history.

For Git projects, retain head/refs, staged entries including modes, staged content,
object/history hashes and the index file hash. Use read-only verification that
does not itself refresh the index. J4/J5 require exact fixture/Git bytes. For other
phases, a predeclared client stat-cache exception is allowed only with evidence of
metadata-only change and client origin, unchanged staged content/entries/history
and no checker-caused refresh. Unexplained drift leaves the positive case incomplete.
Runtime/cache allowances must be explicit and outside protected project/client
settings; a new trust entry is not automatically a harmless cache exception.

Do not revert unexplained owner/global configuration changes to an old snapshot.
Stop affected work, retain before/after evidence locally, identify origin where
possible and report the preservation gap. Existing saved-study bytes and scores
must never be altered. Distinguish subject writes, coordinator-allowed edits,
checker side effects and unexplained concurrent changes; unknown cause stays unknown.

Grade mechanical scope/preservation, source-backed knowledge, authority/uncertainty,
loading evidence, ordinary-work maintenance and fresh-reader continuation separately.
Apply an evaluator-only ledger to decisions/rationale/proposals/blockers/next steps
and new source facts at each phase; require all critical items retained accurately
and no material unsupported claims. Exact prose or a canonical link may preserve
knowledge; raw evidence left unlinked does not excuse losing the maintained record.
Record noncritical omissions rather than hiding them in an average. The
[quality protocol](../evals/quality-protocol.md) owns these semantic principles.

Catalog availability, skill invocation/file reads, instruction consultation,
automatic startup loading and context consultation are separate observations.
Use startup/app evidence for automatic loading; trace reads prove consultation.
Self-reports are insufficient. If telemetry is unavailable, use only a maintainer-
accepted explicit-loading route and scope the support claim to it. A new session
must demonstrably read the context before consequential work; its existence alone
is not proof of use. The loaded rule may name the skill even when J2's task does not.

## Receipts and stop/go decisions

Freeze and retain package/version/hash manifest, exact prompts, installation/profile
configuration, fixture/ledger/checker versions, allowed changes, order and budgets.
For every attempt retain terminal status, exit code when available, timeout/startup
failures, requested/observed identities, available traces/screenshots, final response,
before/after context/diffs and preservation/semantic judgments. Desktop receipts
must include start/stop and fresh-session evidence; missing observations remain
unconfirmed. Preserve raw originals locally; public derivatives must exclude
credentials, private paths/account data and unrelated project information.

After Wave 1, publish no automatic readiness claim. Record per-case passes,
failures, incomplete/not-run cases and remaining risks. The maintainer decides
whether to fix/narrow scope or authorize Wave 2 using the unchanged candidate and
accepted protocol. Freeze Wave 2's own case inputs/checker before its subjects run.
Any candidate/configuration change needs a new freeze and an impact-based
revalidation decision; never transfer old passes to changed inputs silently.

G2–G4 close only for accepted combinations with complete positive journey and
upgrade evidence, passing preservation/semantic checks and resolved material
boundary findings. Collaborating-model review is development evidence, not G5
outside review or proof of effort savings. Follow the separate
[outside-contributor packet](../evals/external-validation/README.md) when that work
is authorized. Stable release still requires G1/G5/G6/G7 decisions/evidence and
explicit publication permission.

For review: accept or revise combinations, isolation method, model identities,
allowed Git/runtime exceptions, customization fixtures, time/session limits and
wave stop conditions. Only then prepare a machine-readable freeze and checker
under separately authorized work. This document starts no validation run.

## Preparation evidence

This is a Sol-prepared proposal, reviewed by Claude Opus 5.5 through the existing
subscription CLI. The initial 90-second review timed out without a verdict; the
one focused follow-up completed. Its four material findings led to explicit
credential/app-state isolation, separate upgrade profiles, cross-session memory
exclusion and frozen multi-prompt sequences. Sol inspected and addressed those
boundaries; no additional counterpart review or subject trial was run. Static
repository checks and independent budget arithmetic passed. Those checks do not
prove the proposed isolation mechanisms or native outcomes; execution preflight
must establish them, and the review does not close G5.

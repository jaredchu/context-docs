Status: **proposal for review; execution remains blocked**. Prepared October 11,
2026, from source inspection and read-only host metadata. No runner was installed
or launched, no guest/account was created, and no login, client launch or trial

## Recommendation

Keep Wave 1 on hold while reviewing a **VirtualBuddy-based macOS guest route** as
the first implementation candidate. Its documented guest setup and configurable
hardware make it a plausible base, but an enforceable network boundary is missing.
Do not approve provisioning on the strength of the runner alone. Tart/Softnet has
more explicit network controls, but its inspected startup changes host network
preferences, conflicting with preservation of existing setups.

This is Sol's proposed direction, not a maintainer selection or a completed
Claude review. A qualifying existing separate environment remains an alternative
under the original plan; none was established by the earlier preflight. Rejecting
the guest route leaves execution blocked, rather than authorizing owner-client use.

## Resources and preparation budget

The read-only metadata check observed macOS 27.0.1, 16 GiB physical RAM, ten
logical CPUs, hardware virtualization support and approximately 1.66 TiB available
on the intended storage volume. These are point-in-time observations, not
reservations. VM statistics also showed compressed memory and cumulative swap
activity; they do not prove that a 6 GiB guest fits during daily work.

Keep the [proposed ceilings](v1.0.0-wave1-isolation-setup.md#proposed-route-and-scope-decision)
as review choices: one active guest, four vCPU, 6 GiB RAM, 100 GiB logical per disk,
350 GiB total physical new storage. Host metadata makes further investigation
plausible, not a feasibility pass. Before future provisioning, verify guest
minimums, runner overhead and how each ceiling is enforced.

Ten subject disks, one review disk and one unauthenticated base could total
**1,200 GiB logical** at 100 GiB each. Copy-on-write/sparse storage may reduce
physical use; it cannot guarantee the 350 GiB limit. The implementation review
must name a hard storage boundary for new files only, or return an explicit budget
revision. A proposed new bounded storage image is an option to investigate, not a
created/mounted volume or accepted solution. Monitoring alone does not satisfy
the setup proposal's enforceable ceiling. Do not change existing volume quotas,
partitioning or storage settings to fit the proposal.

Keep the original 120-minute Wave 1 preparation, 22 subject sessions / 4,080 seconds,
one initial 90-second review plus one focused 90-second follow-up, and 90-minute
reporting caps. A complete cumulative preparation-time ledger and remaining
allowance have not been established. No truthful remaining-minute estimate is
available; the maintainer must reconcile time already spent or accept a revised
preparation cap before additional setup work. This document allocates no new time
or model sessions and does not claim that provisioning ten authenticated subject
disks fits the cap.

## Network boundary to review before provisioning

The design must place enforcement outside the subject's writable state and allow
only reviewed authentication/inference traffic. A proxy environment variable or
client tool deny list alone cannot prevent a shell command from bypassing it.
No host firewall, DHCP, routing, trusted certificate, sudo or login configuration
may be changed to establish the boundary under the current preservation scope.
Transient runner devices/processes would still need explicit future setup scope
and evidence that persistent owner settings remain unchanged.

Require an implementation specification covering:

1. **Transport:** the exact runner/attachment and trusted filtering process,
   ownership, configuration, failure behavior and complete device inventory.
   No subject-controlled alternative interface or policy channel.
2. **Destinations:** default deny; host, LAN, sibling guests and evaluator/source
   hosts unavailable; IPv4, IPv6, direct-IP access, DNS, redirects and alternate
   transports addressed. Do not allow a shared CDN/IP range merely because one
   provider endpoint uses it. Hostname policies need protection against rebinding
   and bypass, and service endpoints serving unrelated content need narrower rules.
3. **Separate phases:** frozen download/install access before subject work;
   restricted guest authentication only when authorized; the minimum inference
   policy during trials. No package marketplace, repository, documentation or
   updater access in subject sessions unless separately justified and frozen.
4. **Evidence:** configuration/source hashes, non-secret destination logs and
   ordinary subject-identity probes proving allowed fixture access and denied
   forbidden reads/writes/network requests. No actual protected content is opened
   to demonstrate denial. Local denial alone cannot prove provider-side denial.

[Claude's network documentation](https://code.claude.com/docs/en/network-config#network-access-requirements)
lists `api.anthropic.com`, `claude.ai`/`claude.com` and `platform.claude.com` for
inference/authentication functions, plus separate connector/update/plugin hosts.
Use it as a starting inventory, not a ready-made allowlist: subscription token
refresh and optional services must be mapped on the accepted build. In this
inspection, OpenAI's [authentication guidance](https://learn.chatgpt.com/docs/auth)
establishes subscription login and local token refresh but supplies no complete
endpoint policy for this route. That inventory remains unresolved; broad provider
wildcards or an API-key fallback do not close it.

Provider-side web/retrieval tools can bypass guest network restrictions. The
[Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference)
documents disabled web search, file credential storage and separate memory
generation/use switches. They complement enforcement, not replace it. For Claude,
[permission rules](https://code.claude.com/docs/en/permissions#allow-or-deny-every-fetch)
can deny WebFetch, but artifact/connector access needs separate control;
[settings precedence](https://code.claude.com/docs/en/settings#exceptions-to-managed-settings-precedence)
documents guest-only connector and skill/plugin-sync controls. Review the exact
effective tool catalog, hooks, plugins, MCP, subagents, memory and remote access
on each accepted build without hiding native personal Context Docs discovery.
Nothing in this packet applies these controls to the owner's installation.

The public evaluator may already be represented in model training or remote state;
access denial cannot establish its absence from model knowledge. Record that
residual limit separately from tested local/network denial. The current fixture
checker proves neither boundary and remains unchanged.

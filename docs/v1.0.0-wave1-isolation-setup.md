separate test account, named Codex profile or sibling client profile in the
inspected locations. Current client roots lead to owner state. Two retained
smoke-test Codex homes symlink their credentials to the owner credential file;
they are preserved evidence, not reusable isolated environments. Authentication
was not tested and Keychain entries were not queried.

Both clients' installed Context Docs packages are v0.1.9. Owner memory/session
stores exist, with no explicit memory suppression in the inspected settings.
Codex has configured MCP servers, plugins and managed requirements. Ordinary
owner-identity access reaches the source repository, evaluator and saved studies.
Directory separation alone has not demonstrated a subject-access boundary.

A subsequent metadata-only check found `kern.hv_support = 1`, but no UTM,
VirtualBuddy, VMware Fusion or Parallels application in the checked application
locations. This establishes hardware capability only. No VM runner, guest,
supported guest client build or subscription login is established. Other installed
locations, remote machines and existing VM images were not exhaustively searched.

## Proposed route and scope decision

Use a dedicated **local macOS guest on Apple silicon**, based on Apple's
Virtualization framework, with all owner storage excluded. Apple documents a
[macOS guest sample](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon)
and explicit [host-directory sharing devices](https://developer.apple.com/documentation/virtualization/shared-directories).
The concrete runner/toolchain, guest OS build, licensing eligibility, disk/RAM
limits and compatibility still require review; the sample is not a configured
runner on this machine. No software purchase or new paid model access is proposed.

Proposed resource ceilings are four virtual CPUs and 6 GiB RAM for the one active
guest, 100 GiB logical space per guest disk and 350 GiB total physical storage for
all new base/subject/review disks and receipts. These are review choices, not
reservations or measured runtime requirements. Check the accepted guest's minimums,
actual free storage and host memory pressure before provisioning; stop if the
runner cannot enforce the ceilings or if setup requires exceeding them.

This recommendation changes the bounded plan's **existing-environment-only**
precondition: no qualifying existing environment was found. The maintainer must
explicitly accept that amendment and separately authorize provisioning and
guest-only authentication before either can happen. The current task authorizes
only this document. A supported existing environment with equivalent evidence may
be selected instead; its availability and boundaries must be demonstrated first.

Accept macOS guests as the exact V1/V6 execution configurations before use. Results
would support those guest configurations, not prove every physical-Mac setup or
desktop route. Retain the proposed 22 subject sessions / 4,080 seconds, one active
subject at a time, and the existing coordinator/reviewer caps. Provisioning, native
boundary checks and authentication count against the 120-minute Wave 1 preparation
cap; account for preparation already spent. If the remaining budget is insufficient,
stop for a revised budget rather than cutting isolation or adding hidden sessions.

## Concrete layout and access

The following names describe new, disposable guest storage; none is an existing
owner path or an instruction to create it now.

| Location/identity | Contents and access |
| --- | --- |
| Host coordinator | Source manifests, checker, evaluator ledger, plans, review findings and all historical studies. Never mounted or made readable to subject guests. |
| Unauthenticated guest base | Accepted macOS/runner and native CLI binaries only. No owner files, credentials, Apple/iCloud sign-in, skills, answers or earlier sessions. |
| `V1-journey`, `V6-journey` | Independent guest disks for J1–J5, carrying only actual approved project output between fresh sessions. |
| `V1/V6-upgrade-clean`, `V1/V6-upgrade-custom` | Four independent guest disks, with native v0.1.9 user installations before U1. No journey candidate installation or other upgrade variant is visible. |
| `V1/V6-core-only`, `V1/V6-boundaries` | Four independent guest disks; B1 contains only core, while B2–B4 have the paired package set and separate projects. |
| `development-review` | Separate disk for the bounded Claude checker/setup review. Receives the review packet intentionally; never becomes a subject disk. |
| Each guest's `/Users/wave1` | Native home, client state and Keychain belonging only to that guest. Credentials remain here. Working fixture under `/Users/wave1/work`. |

There are ten independent subject disks and one review disk, prepared serially as
needed from an **unauthenticated** base. Attach only the active disk; do not clone
or roll back logged-in snapshots to duplicate or rewind refresh tokens. This is
a proposed resource cost, not a promise that all disks/logins fit the current cap.
J1–J5 share their one journey disk; U1/U2 share only their own variant disk. B2–B4
remain the existing counted batch, not additional uncounted sessions.

Disable host directory/disk sharing, clipboard/file transfer, host SSH/agent
forwarding, owner Keychain integration and cloud-drive sync for subjects. The
guest must not reach host services or sibling guest disks over the network.
Transfer only a reviewed input bundle before launch, then detach the transfer
device. Subjects receive their current project, selected native packages and
frozen prompts, not `coordinator/`, checker controls, this plan or the repository.

A VM alone does not hide a public evaluator available online. Before subjects,
freeze an enforced outbound policy allowing only required authentication/inference
traffic, deny host/LAN and public source/evaluator retrieval, and disable browsing,
external fetch and inherited integrations through supported client controls.
Map and test remote tools too: a provider-side fetch can bypass guest network
rules. No working network enforcement mechanism or complete endpoint allowlist
has been implemented here. If effective tools can still retrieve the evaluator,
the route is blocked. Disabling integrations changes the tested configuration
and must appear in its support/evidence statement.

Export allowlisted synthetic project outputs and sanitized native evidence only
after the subject exits. Reject escaping paths, links and unexpected files before
host inspection. Never export whole client homes, credentials, Keychain databases
or authenticated guest images into fixtures or public receipts. Keep new raw
evidence privately retained; no cleanup or rollback touches earlier studies.

## Guest-only client and credential configuration

After separate setup authorization, install accepted native CLI builds from their
documented distribution routes and record binary hashes/builds. Earlier host
version/help observations are evidence about the host only. Do not copy the
owner's app configuration or credential store into a guest.

For Codex, use the guest's real home and default native user skill directory
`~/.agents/skills`. Its guest `CODEX_HOME` holds guest-only configuration/state;
a named config profile alone is not a user-skill boundary. Inventory admin/system
skills, plugins and managed requirements as well as both package manifests.
This follows [official OpenAI configuration](https://learn.chatgpt.com/docs/config-file/config-advanced)
and [skill-location guidance](https://learn.chatgpt.com/docs/build-skills).

Proposed Codex guest config fragment, applied only after authorization:

```toml
cli_auth_credentials_store = "file"
web_search = "disabled"

[memories]
generate_memories = false
use_memories = false
```

Use a fresh supported subscription login inside each Codex guest. The resulting
guest credential file must be regular, guest-owned and mode `0600`; never link it
to the host or another guest. Credential refresh is allowed only inside that
guest's state. [Authentication](https://learn.chatgpt.com/docs/auth) documents the
file store; [memory controls](https://learn.chatgpt.com/docs/customization/memories)
document separate generation and use switches. Validate these settings on the
accepted build before treating them as effective.

For Claude, use guest-only `~/.claude`/`CLAUDE_CONFIG_DIR`, native personal skills
and a fresh supported subscription login in that guest. Freeze the actual
Keychain versus credential-file route without exporting secret values. Claude
documents [config-directory-specific credentials](https://code.claude.com/docs/en/authentication),
with an exception for Console sign-ins without an API key. That exception does
not authorize an API-key fallback. An unavailable subscription route stops setup.

In guest-only settings, select `autoMemoryEnabled: false`; freeze
`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` for future subject launches as a second supported
control. [Claude memory guidance](https://code.claude.com/docs/en/memory) defines
these controls. Inventory account-synced skills and effective settings too. Do
not change shared account skill settings or suppress personal skill discovery
and then claim a native user-scope pass. Uncontrolled syncing/loading blocks the
route. User, project and managed sources must all be accounted for.

No guest login may revoke or change the owner's existing service session. Local
file separation does not prove that provider-side boundary. Require supported
concurrent-session behavior and a non-secret owner-session confirmation after
authorized authentication; if effects cannot be established, stop. Never use a
credential export, existing smoke-test auth link, API fallback or extra spending.

## Stop conditions and review decisions

Stop before a client/model launch when a gate lacks evidence, a forbidden input
is reachable, credentials are shared, native skill roots cannot be isolated,
required identity/allowance is unavailable, or preparation exceeds its cap.
Stop on owner setup/study changes and retain the discrepancy without automatic
rollback. Concurrent owner-client cache refreshes must be identified and qualified;
do not silently waive settings, credential or project changes as routine caches.
No retries, extra native smoke sessions or broader route certification are implied.

Review must decide whether the VM route and its ten subject disks are worth the
setup effort, which supported runner/builds and network controls to accept, and
whether the remaining preparation budget needs revision. A distinct candidate
still needs acceptance: current package bytes equal v0.1.9. Rejecting this route
keeps Wave 1 blocked; it does not permit reverting to the owner's installation.

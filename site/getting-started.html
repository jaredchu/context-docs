STEP 02

Set up one project.

Open the project you want to maintain in your coding agent. If you used the clone commands above, use cd to enter your own project folder, then start a new Claude Code session there.

In Codex

$adopt-context-docs

In Claude Code

/adopt-context-docs

The agent inspects existing documentation, reuses a suitable context entry point or creates one, and adds or reuses a maintenance rule in project instructions. It should fit the project's layout, rather than move everything into a new structure.

Starting from older notes? The skill asks the agent to check current-state claims against relevant code or configuration and preserve decisions and unfinished work. A configuration value does not verify runtime behavior. This is part of setup; it needs no extra skill invocation.

Before you move on

  • Find the context entry point: the starting document linked from the README or documentation index. Its actual path is also recorded in the adoption marker.
  • Check that the maintenance rule is in instructions your agent actually loads. The Claude Code reference explains how to confirm this.
  • Review what was written. Correct unsupported claims and keep private or machine-specific information out of shared docs.

You do not need to enable event logging to use this workflow. Existing logging settings are preserved; optional logging is explained in the reference guide.

STEP 03

Work, then save useful changes.

After adoption, a loaded project maintenance rule tells the agent to update context when work changes a decision, the current state or the next step. You do not need to mention Context Docs in every prompt. Review the updates and check that the rule is loaded.

If an update was missed, or you want one explicitly, ask:

{{SAVE_PROMPT}}

Review the changes in your agent or editor. Keep enough detail for the next reader to continue: what is known, why a decision was made, and what still needs doing. Replace stale facts and link to detailed evidence instead of pasting the entire conversation.

This is an illustration, not a required template or an evaluation result. Your agent should use evidence from your project and preserve its useful existing structure.

Choose the right destination.

A public project may need a design decision and test status. Personal notes and local backup paths usually belong elsewhere. Keep credentials out of context documents. Restricted team information belongs in an appropriate restricted location. Check the proposed diff before sharing it.

Open the same project in a new session and ask:

OPTIONAL STORAGE

Keep context local-only.

Choose context excluded from Git when it belongs on your machine. Existing shared setups stay intact unless you request a change. For a local-only setup, ask:

{{LOCAL_ONLY_PROMPT}}

In Claude Code, replace $adopt-context-docs with /adopt-context-docs. The paths are examples; reuse yours. An ignore rule does not stop tracking an existing file or remove old commits. Read the named entry point directly in a fresh session, since searches may omit ignored files.

Local files need your own backup or transfer between machines. Git exclusion does not provide encryption. Keep local content out of shared docs, instructions and journals.

Retain history with optional logging.

A journal can retain significant decisions, checks and corrections as current context changes without Git history. Logging stays off unless you opt in. Auto for local-only context inside Git requires core 0.1.8/adoption 0.1.9 or later. With auto and no existing setting, it qualifies only when both context and journal paths are verified ignored and untracked. An explicit off, enabled setting or another logging method always wins.

{{AUTO_LOGGING_PROMPT}}

Unverified paths leave logging unchanged. Audits stay read-only, and setup creates no event. The journal records selected events; complete document versions still need snapshots or backups. See the full logging guide.

WHEN YOU NEED IT

A few common questions.

The skill does not appear in my agent.

Confirm both complete skill folders are in the selected skill directory and use one installation scope. In Codex, restart if changes do not appear. Follow the installation reference for client-specific checks.

My project already has context documents.

Use adoption to reuse the current layout and equivalent maintenance rules. You should not have to migrate working documentation simply to follow this method.

My context is getting too long or contains wrong information.

Ask for an audit first: it reports gaps without editing files. See the audit and maintenance prompts. Then request a focused maintenance pass to verify claims, consolidate repetition and keep information appropriate to its audience. Review any proposed removals; a short document is not automatically a useful one.

Will this save tokens or prevent factual mistakes?

There is no guarantee of lower token use, accuracy or privacy. The goal is useful context with less manual organization, and the project is experimental. Read the recorded evidence and limits.

How do I report a problem?

Open an issue with the installed skill version (from its folder's VERSION file), expected behavior and what happened. Use a synthetic example or public evidence; do not upload private project context or credentials.
